# confine

`confine` lets a Go program act on a file named by untrusted input, inside one folder, with no
link followed on the way. It imports the standard library and `golang.org/x/sys` alone.

## Install

```sh
go get github.com/birdtable/go-files/confine@latest
```

The full API is on [pkg.go.dev](https://pkg.go.dev/github.com/birdtable/go-files/confine).

## How it works

Programs call the standard library's `os.Root` themselves, and `confine` holds only what `os.Root`
does not do. `os.Root` keeps an open inside its folder, but it follows a link with a relative
target that stays inside the folder; one with an absolute target it refuses, wherever it leads.
A repository that commits `state -> .git` would carry a write to `state/HEAD` into `.git/HEAD`. `confine` is narrower: it follows no link at all on a path it opens or moves, and
nothing else. Which names a program ignores, what it locks and what it writes stay with the
program.

To ask whether a path is inside a root, use `filepath.Rel` and `filepath.IsLocal`, then open the
name through the `*os.Root` you already hold, so the file system and not the string decides about
links.

## What it holds

| call | what it does |
|---|---|
| `Local(p)` | Takes a slash path from outside (a flag, a file, an environment variable) and gives the name a root takes, in this system's form. It refuses `..`, an absolute path, an unclean path, `.`, a backslash, a colon, a NUL and a component named `..namedfork` in any case (a file's fork on macOS) on every system, so a path means the same everywhere. It refuses a reserved name such as `CON` on Windows, through `filepath.Localize`. `""` is the root, `.`. |
| `NoLinks(root, name)` | Walks `name` by handle, component by component: each is looked at with `Lstat` in the folder opened before it, and each folder is opened and checked to be the one looked at, so no component is resolved by name twice. It refuses a link or a junction at any component, the last included, a component before the last that is not a folder, and a folder that changed between its look and its open. It gives back what the last component is, or nil when it is missing. |
| `Open(root, name, flag, perm)` | Opens `name` as `root.OpenFile` does, with no link followed at any component. On Linux the kernel resolves the name (`openat2`), and on macOS it is `openat` with `O_NOFOLLOW_ANY`. Elsewhere it is the walk, then an open of the last component in the last folder the walk holds, then a check of what opened. It refuses a file with a second name (a hard link) opened to be written, and `O_TRUNC` empties the file only after every check. The open never waits: on Unix it is made with `O_NONBLOCK`, so a pipe at the name opens at once to be read, or is refused at once (`ENXIO`) to be written with no reader, and the caller's check of what it opened refuses it; a regular file or a folder reads and writes as without. |
| `ReadCapped(root, name, limit)` | Reads the file `name` and answers its bytes, opened as `Open` opens it, read-only, and read from that handle alone. A link or junction at any component, the last included, and a name that is not clean and local, are refused with an `*fs.PathError` matching `ErrOutside`; what opened as anything but a regular file (a folder, a pipe, a device), by the handle's `Stat`, matching `ErrNotRegular`, so a name swapped for one after a look is never read; a socket, which the open itself refuses, with the system's own error and not `ErrNotRegular`, nothing read; a file longer than `limit` bytes matching `ErrOverCap`, told by reading `limit`+1, so no more is ever read. A file of exactly `limit` bytes is answered whole, and a `limit` below zero is `fs.ErrInvalid` with nothing opened. The cap is on what is read, so a file that grows while it is read is refused once it passes `limit`. A file with a second name, by a hard link, is read as any other: `Names` is the caller's to ask. |
| `IsRunnable(root, name)` | Answers whether this system would run the file `name` in `root` for this account, from the file itself, opened as `Open` opens it, read-only, then answered by `IsRunnableFile`, and from nothing outside the root. A link or junction at any component, the last included, is refused with false and an `*fs.PathError` matching `ErrOutside`: a file read through a link is not answered confined. A name swapped for a link during the call is refused or answered as the file opened, never read outside, and a pipe or a device is false at once. An open that fails, a file this account may run but not read included, is false with its error. |
| `IsRunnableFile(f)` | Answers whether this system would run the open file `f` for this account, and nothing else: for whatever file `f` is, so how `f` was opened, and whether it stayed inside a root, is the caller's business. Anything but a regular file is false with no error. On Unix it is the exec bit that applies to this account by the open file's `fstat`: the owner's for the owner, else the group's for an account in the file's group, primary or supplementary, else other's, and root's, euid 0, any one; access lists, mount options and capabilities are not read, so a 0755 file on a `noexec` mount is answered true, and so may a file be for a root without `CAP_DAC_OVERRIDE` over it (a user namespace's root on a file whose owner is not mapped into it, or a root with the capability dropped), though running it is refused. On Windows it is the long name the handle gives, whatever the caller spelled (a short name, a trailing dot or space), whose extension must be one `PATHEXT` lists, without case, or Go's own `.com`, `.exe`, `.bat` and `.cmd` when it is unset; no extension is false, and a file with several names, by hard links, is answered by the one the handle gives. That is stricter than `exec.LookPath` on an absolute path, which follows links, and on Windows asks only for a dot, so it answers `README.md` runnable and runs `foo.exe` for `foo`. |
| `Names(root, name)` | Answers how many names the file `name` in `root` has, by hard links, from the file itself, opened as `Open` opens it, read-only, then counted by `NamesFile`, and from nothing outside the root. A link or junction at any component, the last included, is refused with an `*fs.PathError` matching `ErrOutside`, whether it leads outside the root or stays inside it. A name swapped for a link during the call is refused or counted as the file opened, never read outside, and a pipe is refused at once. An open that fails is 0 with its error. |
| `NamesFile(f)` | Answers how many names the open file `f` has, as its volume reports them: `st_nlink` by `fstat` on Unix, `NumberOfLinks` by `GetFileInformationByHandle` on Windows. Only a regular file is counted: a folder, a pipe, a device or a socket is refused with an `*fs.PathError` matching `fs.ErrInvalid`. A count the system will not give is its error, never 1. A volume that cannot hold a second name, as FAT, reports 1, and a network volume reports what its server sends. A name made after the count is not seen, so a guard holds the handle it counted through to its act, as `Open` does for a file opened to be written. `write`'s log and `treesum`'s hash count by it on Windows, and `treesum` on every system. |
| `Mkdir(root, name, perm)` | Makes each missing folder of `name` and answers the last as an `*os.Root`, with no link followed at any component. Each folder is made in the folder above it, then opened by `Open` and checked; a link, or anything not a folder, at any component is refused, and nothing is made through it. A folder this call made must still be one when opened, this account's, and empty, and on Windows hold the owner-only list it was made with, read from the opened handle: one swapped in for it before its mode is set (a link to a file or to a folder, or a folder renamed in from beside it that is another account's, holds anything, or on Windows has any other list) is refused, and its mode is not changed and nothing is removed. A folder made that holds anything, swapped in or filled by another process, is refused with `ErrNotEmpty`, which matches `ErrOutside`. One swap is not refused: an empty folder of this account, renamed in at the name by an account that may write the folder above, is taken as the one made and given `perm`, since `mkdirat` answers with no handle and nothing tells that folder from a new one. A sticky folder above, as a shared one is, refuses another account that rename. The answered root is held, by `os.SameFile`, to be the folder opened and checked. On Unix `perm`, the nine permission bits, is set exactly on each made folder's own descriptor, whatever the umask, keeping a setgid bit the folder takes from the one above, and the folder above each one made is flushed. A folder that was there keeps its mode. A mode beyond the nine bits, or one that does not give this account read and search (`0o500`), is `fs.ErrInvalid`, and nothing is made. |
| `MkdirPrivate(root, name)` | `Mkdir(root, name, 0o700)`, on every system: a folder only this account reaches. |
| `MkdirShared(root, name)` | A folder other accounts reach. On Unix `Mkdir(root, name, 0o755)`. On Windows each missing folder is made with no access list of its own, so it inherits the folder above's inheritable entries, as a folder any program makes there does: who reaches it is that folder's say, which can be wider or narrower than 0o755. A folder it made must still be a folder when opened, this account's, or Administrators' where the token is elevated, and empty; it is not held to the owner-only list, but every entry of its list must be inherited, so one with an entry of its own or a protected list is refused with `ErrOutside`, and so is every folder made under a folder above with no inheritable entry, which Windows gives the token's default list; the check reads that an entry was inherited, not from which folder. A link, a junction or anything not a folder at any component, and a folder of another account or one holding anything swapped in for one made, are refused with `ErrOutside`; a volume that keeps no access lists with `ErrNoAccessList`, at the first folder to make. |
| `MkdirFresh(root, prefix)` | One new folder in `root`, `MkdirPrivate`'s in every respect, under a name it picks: `prefix` and 64 bits from `crypto/rand` in 16 lower-case hex digits, a name `Portable` passes; answered opened, with its name. A prefix the name could not pass `Portable` with, or `.git` in any case, is refused matching `fs.ErrInvalid` before anything is made. The make fails on a taken name, a link among them, which is never opened and is tried again under another; after 16 taken, refused matching `fs.ErrExist`, and nothing made. One level alone; removing or moving it (`RenameNoReplace(root, name, to)`) is the caller's. Not promised: the folder is the owner's alone, but its name is `root`'s, which an account that can write `root` can rename or remove; the answered root stays the folder made, and a caller that needs the name to stay judges `root` with `trust` first. |
| `RenameNoReplace(root, from, to)` | Moves a name to one that is not there. A name that is there is `fs.ErrExist`, and nothing is replaced. On Linux, macOS and Windows: elsewhere, FreeBSD included, it refuses with `errors.ErrUnsupported`, and nothing moves. |
| `RenameExchange(root, a, b)` | Swaps two names that are both there, in one step. Where the system or the file system cannot, it is `ErrNoExchange`, which matches `errors.ErrUnsupported`, and nothing moves. |
| `Remove(root, name)` | Removes `name`, a file, a link or an empty folder, with no link followed at any component before the last; a link or junction at the last is removed as the link, and what it leads to is left. The folder `name` is in is opened by `Open` and held, as a root of its own, to be that folder, as `Mkdir` holds one, and the removal is made in it. A missing name matches `fs.ErrNotExist`; a full folder is the system's own refusal. On Windows a file another process holds is tried again for about 600 ms, the window `write.File`'s rename takes, and a read-only file is removed; past the window the refusal is an `*fs.PathError` matching `fs.ErrPermission`. |
| `RemoveAll(root, name)` | Removes `name` and everything beneath it, under `Remove`'s refusals of the name. A link or junction met in the tree is removed as the link, never walked into, and each folder of the tree is opened as the walk opens one, held to be the folder looked at, or refused, matching `ErrOutside`. A missing name is nil, as `os.RemoveAll` answers. Each name is removed as `Remove` removes one, and the first error ends it. |
| `RemoveAllOwned(root, name)` | `RemoveAll` for a tree the caller made and owns, as a run's own home is, that a program in it may have left read-only, as the go command leaves a module cache. On Unix each folder of the tree this account owns, by its effective uid, that lacks its owner's write bit is given it (u+w) and no other, by `fchmod` on the folder opened and held to be the folder looked at, before it is emptied. A folder without its owner's search or read bit keeps its mode and is the system's refusal, as `RemoveAll`'s is. A folder another account owns keeps its mode and is removed as `RemoveAll` removes it; a link in the tree is never followed or changed; a folder swapped in is refused, matching `ErrOutside`, before its mode is touched; the folder `name` is in is not changed. On Windows it is `RemoveAll`, which removes a folder or file with the read-only attribute already. The first error ends it, and each folder given the bit before it keeps it. |
| `LinkFolder(root, target, at)` | Makes `at` a link to the folder `target`, one call on every system: a symbolic link on Linux, macOS and FreeBSD, made by `symlinkat` from `at`'s folder opened as `Open` opens, and a junction on Windows, which needs no privilege, made by handle (below). It refuses `at` as the renames refuse a name, a name already there with `fs.ErrExist`, and a `target` that is not a clean absolute path to a folder, with an `*os.LinkError` matching `fs.ErrInvalid`. On NetBSD and the others it refuses with `errors.ErrUnsupported`, and makes nothing. |
| `LinkFile(root, target, at)` | Makes `at` a symbolic link to the file `target`, never a hard link or a copy: on Linux, macOS and FreeBSD as `LinkFolder` makes one, and on Windows set by handle on a new file made as `LinkFolder` makes its folder (below), which takes the privilege to make a symbolic link, as Developer Mode gives. Where this account does not hold it, the file made is removed by its handle and it refuses with `ErrNoFileLink`, which matches `errors.ErrUnsupported`, as on NetBSD and the others. It refuses `at` as `LinkFolder` does, and a `target` that is not a clean absolute path to a regular file, with an `*os.LinkError` matching `fs.ErrInvalid`. A refusal makes nothing. |
| `CopyTree(dst, src)` | Copies everything in `src` into `dst`, root to root, each name walked by handle with no link followed: each folder made as `Mkdir` makes one, 0o700, the owner-only list on Windows, each file written 0o600, or 0o700 where `IsRunnableFile` answers the source runnable, the modes set whatever the umask; times, owners and hard links are not kept. Each link that leads inside `src`, as `Below` says from `src`'s `Name`, is made again to the same name in `dst` once every folder and file is there: as `LinkFolder` makes one to a folder, a junction on Windows, and as `LinkFile` does to a file, `ErrNoFileLink` where this account may not make one. Its target is relative to its own folder on Linux, macOS and FreeBSD, so the copy can be moved and read through an `os.Root`, and absolute under `dst`'s `Name` on Windows, as a junction needs, so there the links hold only while `dst` keeps its `Name`. The target is the link's own spelling, so a copy from a volume that ignores case to one that does not may refuse a link spelt otherwise than the name on disk. It refuses, matching `ErrOutside`, a link that leads outside `src` or through more than 32 links, a root whose `Name` names another folder than it holds, `src` and `dst` one folder, `dst` met in the walk of `src`, and a reparse point on Windows that is neither a link nor a junction; matching `fs.ErrInvalid`, a root whose `Name` is not absolute and clean, and a pipe, a device or a socket, a file swapped for one before its open among them; matching `fs.ErrNotExist`, a link that leads to nothing; and matching `fs.ErrExist`, a name already in `dst`, which is left. The first error ends it, and what it made stays for the caller's `RemoveAll`. |
| `Resolve(path)` | Answers an absolute `path` with every link on it followed, one hop at a time, as the system follows them: a symbolic link everywhere, and a junction on Windows, which `filepath.EvalSymlinks` has not followed since Go 1.23. No ownership is judged. `path` need not be clean, and is taken where the system takes it: on Unix it is walked as written, so `tree/d/../x`, with `d` a link, is the `x` beside `d`'s target, and a `.` or an empty name is stepped over; on Windows, which takes a `..` by its spelling before it opens anything, it is walked as `filepath.Clean` gives it, so `tree\junc\..\x` is `tree\x`, whatever `junc` is, but a device path (`\\?\`, `\??\`, `\\.\`), whose names the system takes as written, is taken only clean, and an unclean one is refused, matching `fs.ErrInvalid` and `ErrOutside`. A path the system itself refuses, as a trailing separator after a file, is refused with the system's own error. Each name is looked at with `os.Lstat` below the part already walked; a link's target, read with `os.Readlink`, goes in front of the names still to walk, so a link among its own names is followed too, and a relative target is taken against the link's own folder. No path is cleaned before its links are read: on Unix a `..` in a target goes up from the folder the walk reached, so `d/../x`, with `d` a link out, leads out; on Windows the system takes a `..` in a relative target by its spelling, and so does `Resolve`. A target rooted with no drive (`\x`) is on the link's own volume; a mount point of a whole volume is kept as a folder where the mount manager lists it among the volume's paths. Names below the last that exists are kept as written. Once the walk ends, the system's own `os.Stat` of `path` must find the file at the answer, or the path is refused as changed, with `ErrChanged`. Where the answer has a missing name, the system must find nothing there too, and any other answer of its, a folder another process made there while the path was walked among them, or on Windows the failed open of a file link to what is now a folder, is refused as changed; that is all that is checked: the missing tail is where the walk leads, not where the system would make a file, and the two differ for a link the walk reads otherwise than the system follows it, as a `/proc` link of a process in another mount namespace, or on Windows a symbolic link to an NT name with no drive (`\Device\...`). It refuses, matching `ErrOutside`: a path that is not absolute (`fs.ErrInvalid` too), more than 32 links (`ErrLoop`), and on Windows a target on a drive with no root (`C:x`), an absolute target with a `.` or a `..`, a target with a name that ends in a dot or a space, a junction whose target is not absolute, a device path (`\\.\`), a target past `\\?\` that is not a whole volume or names one not mounted at the link, and a reparse point that is neither a link nor a junction, never matching `fs.ErrNotExist`. A `..` after a missing name is `fs.ErrNotExist`. The answer is a name read now: to act on a file, open it with `Open`. |
| `Below(folder, path)` | Answers the name of `path`, absolute and clean or not, resolved as `Resolve` resolves it, in `folder`, in this system's form, `.` for `folder` itself; `folder` is absolute and clean, or refused matching `fs.ErrInvalid`. Each folder of the answer, from the last up to the top of its volume, is compared with `folder` by file ID, as `os.SameFile` compares them, never by spelling, so an 8.3 short name, another case on a volume that folds case, and a link to `folder` all name it. A path not in `folder` is refused, matching `ErrOutside`. A Windows folder on the walk whose 64-bit index reads zero (a WebDAV or SMB drive) or all-ones (ReFS, with no 64-bit form of its 128-bit ID) gives `os.SameFile` nothing to tell it apart by, so it is refused with `ErrNoFileIndex`, the one value `write.ErrNoFileIndex` is, matching `errors.ErrUnsupported`; the same guards `Collide`'s and `Mkdir`'s compares by file ID. |
| `Final(path)` | Answers the system's own name for the folder or file an absolute `path` opens, read from a handle open on it and never built from `path`'s spelling, so two spellings of one file answer the same bytes: on Windows an 8.3 short name and another case give the long name in its stored case, and on macOS another case gives the stored case. A caller that keys a record by a path keys it by this answer. Every link before the last name is followed, as the system follows it, and a link at the last name is not: it answers its own name, in the folder the system names, and so does a link to nothing; to name what a link leads to, pass `Resolve`'s answer. Windows answers from `GetFinalPathNameByHandle`, its normalized name with the drive, without the `\\?\` prefix where the name is shorter than `MAX_PATH` and `GetFullPathName` gives it back unchanged, and with it for a name that ends in a dot or a space or is a device's; macOS from `fcntl`'s `F_GETPATH`; Linux from the link `/proc/self/fd/<n>`, read under that folder held to a procfs by `fstatfs`. Off those three, and where the call fails or answers no absolute path, as on Linux with no `/proc` or with a `/proc/self/fd` that is not a procfs, it is an `*fs.PathError` matching `errors.ErrUnsupported`, never `fs.ErrNotExist`. The answer is looked at with `os.Lstat` and held against the open file by `os.SameFile`: a name that is no longer the file opened is refused with `ErrChanged`; on a Windows volume that gives no file index `os.SameFile` has nothing to compare, so there the answer is not held against the file. A file with a second name, by a hard link, answers on Linux and Windows the name it was opened by, as does a file reached through a bind mount on Linux; macOS's `F_GETPATH` answers whichever of a file's names any process looked at last, which may be in another folder, so on macOS a file, not a folder, with more than one name is refused, matching `errors.ErrUnsupported`. On Linux, in a folder that folds case (`Folds` tells it), the kernel answers the spelling the name was first looked up by since it entered its cache, which may not be the stored one, so a caller keying a name there folds the answer itself. It refuses a path that is not absolute, matching `fs.ErrInvalid` and `ErrOutside`, and a name not there with the system's error, matching `fs.ErrNotExist`; on macOS, whose open for `F_GETPATH` needs read access, a file or folder this account may not read is refused with the system's error, matching `fs.ErrPermission`, where Linux, opening with `O_PATH`, answers it. The answer is a name read now: a rename after it is not seen. |
| `FileURL(goos, abs)` | Answers the `file:` URL of an absolute path on the system `goos`, as Go's own `go` command writes one: `/a/b` is `file:///a/b`, `C:\a\b` is `file:///C:/a/b`, and the share path `\\host\share\a` is `file://host/share/a`. Each name is escaped, so a `?`, `#` or `%` in it stays in the name. It refuses, matching `fs.ErrInvalid`, a path that is not absolute, a `.` or `..` element, a NUL byte, and on Windows a device path (`\\?\`, `\\.\`) and a share with no host or share name. A system with no form here matches `errors.ErrUnsupported`. It reads no file and takes the system as an argument, so a URL for another system is made on any. |
| `FromFileURL(goos, uri)` | `FileURL`'s inverse. It refuses, matching `fs.ErrInvalid`, another scheme, a user, a port, a query or a fragment, the short forms `file:/a` and `file:a`, any host but `localhost` on a system but Windows, a drive as the host on Windows (`file://C:/a`), a backslash on Windows, a path that is not absolute, a `.` or `..` element and a NUL byte, escaped or not. On Windows it also refuses an element Windows reads as another name than the one written, though `FileURL` writes it as given: one ending in a dot or a space, which the Win32 name rules strip (`file:///C:/a/.%20` would open `C:\a`), one holding a colon past the drive, a stream of another file, and a device name, `CON`, `PRN`, `AUX`, `NUL`, `COM0` to `COM9`, `LPT0` to `LPT9`, `COM` or `LPT` with a superscript 1, 2 or 3, `CONIN$` or `CONOUT$`, in any case, with or without an extension, as Windows before 11 reads `CON.txt` as `CON`; and a host that is `.` or `..`, or that starts with `;`, which names a redirector, so the open reaches the host the next element names (`file://;LanmanRedirector/host/share/a`). An 8.3 short name (`file:///C:/PROGRA~1/x`) passes, as its spelling does not tell it from a plain name: a caller that matches paths resolves them first and compares by file ID, as `Below` does. On Windows a host names a share, which Windows reaches over the network with this account's credentials when it is opened: a program that takes a URL from a less-trusted source refuses a path that begins `\\` before it opens it. |
| `Nearest(start, marker, top)` | Answers the nearest folder, at `start` or above it, that holds `marker`, as an absolute path. `marker` is taken as `Local` takes it and may be several names (`.app/pin.yaml`); an empty one is refused too, matching `ErrOutside`. `start` is made absolute and cleaned and walked up by its own names, with no link in it resolved: pass `Resolve(start)` for the walk of the real folders. Each folder is asked with `os.Lstat`, so a marker that is a link counts, a dangling one too. A folder without the marker, or whose marker's inner name is not a folder, sends the walk up; any other error stops it and is returned. `top` is the last folder asked, `""` the top of the volume (`/`, `C:\`, `\\host\share\`); a `top` that is not `start` or above it, spelled as the walk spells it (in the same case on Windows too), is refused before any look, matching `ErrOutside`. With no marker, an `*fs.PathError` naming it, matching `fs.ErrNotExist`. The answer is not judged: a marker in a folder another account owns or may write is found like any other (git's CVE-2022-24765), so a caller that will confine to it hands it to `trust.Path(dir, trust.Folder, who)` first, or names a `top` it trusts. |
| `Readlink(root, name)` | Answers the target of the link at `name`, one hop, as the link holds it: not resolved, not cleaned and not judged, so a relative target stays relative to the link's own folder, and any target may lead outside the root; `Resolve` or `Below` says where it leads. `name` is clean and local, as `Local` gives it; `.` is refused, matching `ErrOutside`. The walk to `name`'s folder is `NoLinks`'s: a link, junction or other reparse point at a component before the last is refused, matching `ErrOutside`. A symbolic link is a link on every system, and on Windows so is a junction, spelled as `os.Readlink` spells it (`C:\dir`, `\\host\share\dir`, the stored text of a relative one, `\\?\Volume{...}\` for a mount point of a whole volume). Each refusal is an `*fs.PathError` with `name` slash-separated: not there matches `fs.ErrNotExist`; there and no link, a file or a folder, matches `fs.ErrInvalid`, which `os.Root.Readlink`'s bare `EINVAL` does not; a link that cannot be read, as on Windows a reparse point that is neither a link nor a junction, which `os.Readlink` answers as not there, or one that changed as it was read, matches `ErrOutside` and never `fs.ErrNotExist`. |
| `ErrLoop` | `Resolve`'s and `Below`'s refusal of a path that passes more than 32 links, macOS's own limit and the lowest of the systems'. It matches `ErrOutside`. |
| `ErrChanged` | `Resolve`'s, `Below`'s and `Final`'s refusal of a path that changed while it was walked: the system's own look found another file than the walk, something where the walk found nothing (a missing name another process made meanwhile among them), or a folder of the walk was another file when its file index was read, or the name the system gave `Final` for the file it opened is not that file. It tells a path that changed under the walk from one that leads outside, never that the change was harmless. It matches `ErrOutside`. |
| `ErrNotEmpty` | The refusal of `Mkdir`, `MkdirPrivate`, `MkdirShared` and `MkdirFresh` of a folder the call made that holds something when it is opened and checked: another process put a name in it, or swapped in a folder that holds one. Nothing was done to it. Another account's folder, a link and what is not a folder stay `ErrOutside` alone. It matches `ErrOutside`. |
| `Portable(name)` | Answers whether `name`, one name in a folder, means one file, and the same one, on every system, by the strictest of their rules on every host, and its key: the form two names share when a folder that folds case or normal form reads them as one, so `Makefile` and `makefile` have one key, and so do `café` composed and `cafe` with a combining acute. The key is the name decomposed, folded a character at a time and composed again, by `golang.org/x/text/unicode/norm`, the one library beside `golang.org/x/sys` that `confine` links. It looks at nothing on disk. It refuses, matching `fs.ErrInvalid`: an empty name, `.`, `..`, a name that is not UTF-8 or is over 255 bytes; a control character and any of `/ \ : * ? " < > \|`; a trailing dot or space; a name Windows keeps for a device (`CON`, `NUL.txt`, `COM1`, `LPT¹`, `CONIN$`); an 8.3 short name (`GIT~1`); a format character, the HFS+ ignorable code points among them; a default-ignorable character, which shows as nothing and no normal form removes (the combining grapheme joiner, a variation selector, a Hangul filler); a character whose full case folding is several (`İ`, `ﬁ`, `ᾳ`), but for `ß` and `ẞ`; `.git` in any case; and a name whose composed or decomposed form one of these rules refuses, as `≮`, which macOS keeps as `<` and a slash. A name in any normal form passes: a combining mark, a conjoining jamo, a Greek Extended letter, a CJK compatibility ideograph and the Kelvin, Ohm and Angstrom signs are settled by the key. The `.git`, 8.3 and HFS+ rules are ported from go-git (Apache-2.0; `NOTICE` names it). |
| `Collide(root, a, b)` | Answers whether the folder `root` reads `a` and `b`, two names in it, as one file. It answers for the volume and the folder, not the system: APFS as macOS formats it folds case and takes é composed and decomposed for one name, NTFS folds case alone, ext4 folds neither, and a folder may be set otherwise. Each name is looked at with no link followed: both there and the same file is true, both there and two files, or one there alone, is false. Where neither is there, `a` is made, empty and the owner's alone, `b` is looked at, and `a` is removed again. A file another puts at `a` in that time is left there only up to the last instant before the remove: the probe is held open from its make until after the remove, so no file put at `a` or `b` can take its file ID, as ext4 hands a freed one out again at once, and it is looked at by that ID, then removed by name, as no call removes a file by its ID, so a file put at `a` between that look and the remove is removed. It refuses, matching `ErrOutside`, a name that is not one name in the folder: empty, `.`, `..`, or one holding a separator. |
| `Folds(root)` | Answers how the folder at `root` reads names, as a `Folding`: `FoldNone`, `FoldCase`, `FoldComposition` (é composed and decomposed as one name), `FoldBoth` or `FoldUnknown`, and writes nothing. macOS asks the volume's type and case sensitivity: APFS and HFS+ that fold case fold both, case-sensitive HFS+ folds composition, and case-sensitive APFS, which may be made either way, is `FoldUnknown`. Windows asks the volume's file system and case-sensitive-search flag and the folder's own case-sensitivity flag: NTFS, ReFS, FAT and exFAT on a local disk fold case unless the folder is set case-sensitive, and a flag that cannot be read folds case. Linux asks the file system's type and, on ext4, f2fs and tmpfs, the folder's casefold attribute, which folds both; btrfs folds neither. Any other volume, a network share, FUSE, XFS and ZFS among them, and any other system, is `FoldUnknown` with an error matching `ErrNoFolding`, which matches `errors.ErrUnsupported`; a failure to ask is `FoldUnknown` with the system's error, and a `root` that is not a folder is `FoldUnknown` matching `fs.ErrInvalid`. `FoldUnknown` holds both fold bits, so `FoldsCase` and `FoldsComposition` answer true for it: treat it as `FoldBoth`. The answer is the folder's rule when asked; `Collide` asks by a probe. |
| `ErrOutside` | What every refusal of a path matches. |
| `ErrNoExchange` | `RenameExchange`'s refusal where no swap in one step is made. |
| `ErrNoFileLink` | `LinkFile`'s refusal where no symbolic link may be made: on Windows by an account without the privilege, and on NetBSD and the others. It matches `errors.ErrUnsupported`. |
| `ErrNoMode` | `Mkdir`'s refusal on Windows of a `perm` without owner read, write and search (0o700), or with a bit beyond the nine permission bits, as a folder there has the owner-only access list, not a mode: nothing is made. It matches `errors.ErrUnsupported`. |
| `ErrNoAccessList` | `Mkdir`'s refusal of a folder to make on a Windows volume that keeps no access lists (FAT, exFAT), where it would be every account's, on a share that will not take this account as the owner or a volume that will not say whether it keeps lists, and where this account cannot open by name what it makes with that list (a restricted token or an AppContainer the list does not name, a share that knows this account by another SID). It matches `errors.ErrUnsupported`. This is tried first on a throwaway folder beside it, `.probe-` and random letters, made and removed, and only where the name is not there already: a process killed in that instant leaves it, empty, and it is the caller's to remove, and so does a removal of it that fails, with an error that names it and is `ErrNoAccessList` only where it could not be opened by name either. Where the cause is a denial, it matches `fs.ErrPermission` too, so test `ErrNoAccessList` first. |

Each of `Open` and the renames refuses, matching `ErrOutside`, a link or junction at any component
of a name, the last included, a name that is not clean and local, a component named `..namedfork`, and a file with a second name,
a hard link (`Open` only when it opens the file to be written): a hard link to a file elsewhere in the root is that file, and no walk sees it. The
renames and the removes refuse the root itself as a name. `Remove`, `RemoveAll` and `RemoveAllOwned` refuse, matching `ErrOutside`,
a name that is not clean and local, a link or junction at any component before the last, and on
Windows a component that ends in a dot or a space, as the renames refuse it.

A refusal at a component is an `*fs.PathError` of op `walk` naming that component, so a caller
finds it with `errors.As`, never by the text. When the kernel refuses, a walk afterwards names the
component; it decides nothing.

On Linux and macOS the two renames act through descriptors of the folders the names are in, each
opened by `Open`'s kernel call, and the system's call follows no link at either last component.
On Linux any answer of `openat2` but `ENOSYS`, a seccomp filter's `EPERM` included, is final: the
walk is never tried in its place. A kernel with no `openat2` has `Open` walk.

A file's second name is counted from the stat on Unix and from the open handle's information on
Windows, where any account that may write a file may give it a second name.

**What remains.** On Linux and macOS no link is followed by `Open`: the kernel refuses a component
swapped for a link at any moment, and a test swaps one in at the open through a seam, where the
walk alone opens the same file from the folder it already holds. A second name is still a check made after the open: a hard
link made to the file once that check has passed is not seen, and the caller writes to a file with
two names.

Where `Open` walks, it walks by handle: each folder is opened from the one before it and checked
to be the folder its look found, so a folder swapped for a link between two steps, one that stays
inside the root as much as one that leads out, is refused, and a test swaps one in there through a
seam. The look at the last component is a check before a use, so it checks again after it opens:
a process that does not take the caller's lock can swap the last component for a link between the
look and the open. `os.Root` keeps that open inside the folder. `Open` refuses an existing file
unless it is the one the walk found. A missing file is made by an exclusive create in the folder
the walk holds, never where a link leads, and refused unless a second walk finds that file at its
name with no link on the way; a refused file is left there, empty, before a byte is written. The
walk is deleted when the standard library gains `os.O_NOFOLLOW_ANY`.

A rename on Linux or macOS acts in the folders the kernel opened, wherever in the root a swap has
since moved them. Its last components are looked at from those folders before the call: a hard
link given to the file in between is not seen.

A rename on Windows is by handle. Each folder of either name is opened from the folder before it,
from the root's own handle down, with no reparse point followed, and refused when it is a junction
or another reparse point; each is held open with no share to delete, so while the rename runs no
process can move it, or a folder above it, and put a junction in its place, which needs no
privilege. A test tries that through a seam between the hold and the move. The source is opened
from its held folder, with no share to delete, and refused when it is a reparse point or a file
with a second name; it is moved with `NtSetInformationFile` and `FILE_RENAME_INFORMATION`, its
`RootDirectory` the held folder of `to` and `ReplaceIfExists` false, so the system refuses a name
made at `to` since the look. `SetFileInformationByHandle` refuses a `RootDirectory` on Windows 11
26200. The root's own folder is the anchor and is not held: moved, it takes
the whole tree with it, and nothing leaves the root. A name with a component that ends in a dot or
a space is refused before any call, with an error matching `ErrOutside`: the Win32 name rules
that `os.Root` takes strip both, so `x.` is `x` there, while the NT calls take `x.` as
written, and one name would mean two files. `filepath.IsLocal` takes such a name. A hard link given to the file once its handle
is read is not seen, as on Linux and macOS.

`LinkFolder` on Windows is by handle too. The folders of `at` are held as a rename holds them, from
the root's own handle down, each refused when it is a junction or another reparse point. The new
folder is made in the last of them by `NtCreateFile` with `FILE_CREATE`, so it is new, and a name
there, a junction included, is `fs.ErrExist` and is not followed. The mount point is set on that
folder's own handle. A folder the system refuses the mount point on is removed by the same handle,
so the folder removed is the one made, and a test refuses the set through a seam. The data, the
target in the object manager's `\??\` form and as written, is refused before any folder is made
when it would pass the system's 16 KiB. A target must be on a drive letter that `GetDriveType`
says is a fixed or removable disk, that `QueryDosDevice` says is a device, not a `subst`
folder, whose root `GetVolumeNameForVolumeMountPoint` names a volume at, and that
`GetVolumePathNamesForVolumeName` lists among the paths that volume is mounted at: a share (`\\`)
or a letter mapped to one, which a junction cannot reach, and a `subst` letter or one
`DefineDosDevice` made with a raw target, to a folder or to a whole volume, which name it in one
logon session only, are refused, each with an error matching `fs.ErrInvalid`, a failed look at
the letter included. So is a letter every session sees that the
mount manager did not make, one `Session Manager\DOS Devices` or a driver defines: the list
holds only the letters and folders the mount manager mounted a volume at. A
mounted letter laid over in this logon session, by a link object in its own `\??\` folder, which
needs no elevation where `DefineDosDevice` is refused, is refused too, raw to a folder of its own
volume, to a folder of another, or to another volume: each look reads the letter as this session
does (tried on NTFS and exFAT). Whether a
Windows container's `C:\` is in that list is not yet run: if it is not, every `LinkFolder` there is
refused. A target with a component
ending in a dot or a space is refused as `at` is: `os.Stat` checks it by the Win32 rules, which
strip both, and the junction holds the NT name, which keeps them. Both names are converted to
UTF-16 as `os.Stat` converts them, so an unpaired surrogate, which Go holds as WTF-8, is the
same name in the check and in the junction. The target is looked at once, to be a folder, before the link is made: a link holds
its target by name, and a folder swapped there later is what the link leads to, as with any link.


## What os.Root does not do

These were read against Go 1.27.4 on 15 Nov 2026. A test of this package holds the first three to
the Go it builds with, so a Go that closes them turns that test red.

- `Root.OpenFile` follows a link at a middle component (`state/HEAD` opens `real/HEAD`).
- `Root.OpenFile` follows a link at the last component, even when the caller passes
  `O_NOFOLLOW`. `os/root_unix.go` adds `O_NOFOLLOW` itself and follows the link on `ELOOP`.
- A create through a dangling link, without `O_EXCL`, makes the link's target.
- `Root` takes `a/../b`, and `filepath.Localize` takes a backslash and a colon on Linux and
  macOS. `Local` refuses all three.
- `Root.Rename` replaces a name that is there, and swaps nothing.
- Nothing in `Root`'s set counts a file's names.

`confine` calls these of Go 1.27's `Root` set: `Name`, `Open`, `OpenFile`, `OpenRoot`, `Lstat` and `Stat`,
and adds the walk, the kernel calls and the checks around them.
