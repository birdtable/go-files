# write

`write` replaces a file whole, so a reader sees the old file or the new one and never half of either, and a power cut leaves one of the two. It is one recipe on the standard library's `os.Root`, the same on every system: a temp file beside the name, `.<name>.<16 hex digits>.tmp`, made by an exclusive create; given its owner, its content and its mode on its own descriptor; flushed and closed, a descriptor to read it held till the last check; checked to still be the file written; renamed over the name; and the folder flushed, or on Windows, where a folder flushes only through a handle open to write, the rename written through to the disk. A temp file a killed writer left stays, hidden, for the program to clear: nothing here sweeps a folder.

## Install

```sh
go get github.com/birdtable/go-files/write@latest
```

The full API is on [pkg.go.dev](https://pkg.go.dev/github.com/birdtable/go-files/write). Runnable examples are in [example_test.go](example_test.go).

## How it works

Built on the standard recipe of a temp file beside the name, flushed and renamed over it, over `os.Root` and `golang.org/x/sys`. It adds what the recipe leaves out: the owner and mode set on the temp file's descriptor, the check that the file renamed has the device and inode number (volume serial and file index on Windows) of the one written, the folder flushed (on Windows a rename written through), a log kept under a cap, and a copy kept and put back. The program configures the name, the mode or owner (`Mode`, `KeepMode`, `Owner`, `KeepOwner`), `Check`, `IfHolds`, `NoSync`, `NoReplace` and `Runnable`, and for `Append` the cap, `LogMode`, `Aside` and its context. Windows' rename retry of about 600 ms, `Append`'s tries, and the temp file's name are fixed, as the doc says.

`File` and `FileFrom` go by a path, `FileFrom` reading what it writes from an `io.Reader`. `FileIn` goes by a name beneath an `os.Root`, which refuses a name, or a link or folder swapped in on the way, that leads out of it, at every step, with the `os` package's own error. A link at the name itself is replaced, and what it led to is not touched.

`Append` adds a line to a log kept under a cap: a line that would take the log past it first moves the log to the name `Aside` gives, over the one there; `Append` takes no default name, and without `Aside`, or with `Aside("")`, it is refused with `ErrNoAside` before anything is opened, so where an old log goes is always the program's; a program that keeps more old logs moves its last one on itself before it calls `Append`. A line is never cut, and a log `Append` makes, at first and after each move, is 0600, or exactly `LogMode`'s mode whatever the umask; a log already there keeps its own. `Append` takes `LogOption`s, `LogMode` and `Aside`, a type of their own, so an `Option` it would not read, as `Owner` or `Check`, does not compile. A `LogMode` that does not give the owner read and write, and an `Aside` that is the log's own name, are refused before anything is opened, and no line is written. A link or anything not plain at the name, or at the name aside when the log is to be moved over it, is refused, and so is a log with a second name, counted at the open and again once the log is held, since a hard link can be to a file outside the root. Two processes appending at once each hold the log while they look at its size, move it and write, so no line is lost, and a move by the other writer sends one back to look again, up to 1000 times. A hold another process keeps on the log, a reader's included, is waited on until the caller's context ends, and then refused with the context's error, found by `errors.Is`; with no deadline, `Append` waits as long as the hold is kept. The hold is always tried once, so a context already ended still writes to a log no other process holds. A log whose last byte is not a newline has a torn last line, which a crash in another writer's write can leave: `Append` ends it with a newline put before the new line, in the same one write, so the new line never joins the torn one. The torn line is kept as it is, never cut, and the newline counts toward the cap.

`Keep` makes a copy of a file before it is replaced, at the name the program gives in the folder it gives, `config.toml.v12` or any scheme its own pruning reads, by an exclusive create that never writes over or follows a name that is taken: a taken name, a link among them, is refused with an error matching `fs.ErrExist`, nothing is written, and the program names another. A name that is not one plain name in the folder on every system, as `confine.Portable` judges it, is refused before anything is opened: empty, `.` or `..`, a separator or a colon, or an end in a dot or a space, as Windows reads the first two as another file and strips the last two, a name Windows keeps for a device, as `NUL`, an 8.3 short name and `.git`, on every system. `PutBack` puts a copy back, with its bytes and mode, only over a file that holds what the caller says it wrote after `Keep` (`IfHolds`), hashing and replacing it through the one folder it opened. `KeepIn` and `PutBackIn` do the same by two names, each beneath its own `os.Root`, with the same refusals and the same copy. The two may be one root, or two that share no folder and lie on two file systems: no rename or link crosses them. Every step goes through the root its name is beneath, as `FileIn`'s do, so a folder on the way turned into a link out of it is refused, and nothing outside the two is read or written. The copy's folder must be there, and none is made. With `Gone`, `PutBackIn` puts a copy back where the file was removed, by an exclusive placement that never replaces, with the copy's mode; anything at the name is `ErrChanged`, and `holds` must be zero. Without it a missing file is `ErrChanged`. Pruning old copies is the program's.

`Swap` puts a new program in the place of one that may be running, and keeps the old one at the name the program gives. Windows will not write over or remove a program that runs, but it will rename one, so the old file is moved aside first, then the new one takes its name, and if that second move fails the old one is moved back: the name never ends without one of the two. The three names are plain names in one folder, so the new file is one the program wrote beside the old, by `File` with `Runnable`. Neither move goes over anything: a file at the aside name is refused with an error matching `fs.ErrExist` before anything moves, and a file put at the program's name between the two moves is kept and named in the error; one whose put-back fails too is `ErrNotSwapped`, with the old program left aside. `IfHolds` refuses a program that holds anything else before anything moves, and a file at the name that is not the one it looked at is moved back and refused; so is a file at the new file's name that is not the one it looked at, once it has taken the program's name: it goes back to the new file's name and the old program back to its own. If that undo fails, the error is `ErrNotSwapped` too, and the program's name may then hold that file, which `Swap` never looked at and the caller must not run. A link, a folder or a pipe at either name is refused, never followed. On Unix each move is a hard link and the removal of the first name, so a crash between them leaves both names; on Windows each is a rename by the file's own handle, opened beneath the folder, with no replace, written through to the disk unless `NoSync`, and tried again for about 600 ms while a scanner holds the file. `Swap` takes `IfHolds` and `NoSync` alone, and refuses every other option with an error matching `fs.ErrInvalid`, as it writes no file.

A file is read (by `IfHolds`, `Keep` and `PutBack`) or appended to only when it is a plain file, by a look and again on the opened descriptor, and the open never waits, so a pipe put at the name hangs nothing.

## To follow a link at the name, and write the file it leads to

A write replaces what is at the name, a link included, and follows none, so no option follows a link: a program that keeps its file behind a link, as settings linked into place, asks where the link leads first, and writes there:

    resolved, err := confine.Resolve(path)
    if err != nil {
        return err
    }
    return write.File(resolved, content, opts...)

`confine.Resolve` follows every link on the path, a junction on Windows too, and answers where a link to a missing file leads, so the first write makes the file there. The link is left as it was, and the temp file is beside the target, never beside the link. The answer is a name read now: a link changed between `Resolve` and the write is not seen, and the write goes where the link led. For a write held inside a folder, so that a link leading out of it is refused, take its name below the folder with `confine.Below(folder, path)`, which resolves the path the same way, and write with `FileIn` on a root opened at the folder: the root then refuses, at every step of the write, a link or folder swapped in that leads out. A test in the second consumer writes through a link to a folder and through a link to the file, on every system, the target there or missing.

## What each option does

| option | what it does | refused, and how |
|---|---|---|
| none | the file is 0600 and its writer's; what is at the name, a link included, is replaced; the file and its folder are flushed | |
| `Mode(perm)` | the file's mode, exactly, set on the temp file's descriptor, so the umask does not narrow it | Windows: the file keeps the owner-only access list, below, narrower than `perm`, and `perm` without owner write (0o200) makes it read-only. A `perm` without owner read (0o400), or with a bit beyond the nine permission bits (setuid, setgid, sticky), is `ErrNoMode`, which matches `errors.ErrUnsupported`. `Keep` and `PutBack` give the copy file's own mode, on Windows its read-only attribute, and apply no `Mode`, and refuse one where `File` does; the mode's group bits stay only where the copy is in its source's group, or the group `Owner` gave it, and are cleared where it is not |
| `Shared()` | a file other accounts read: 0644 exactly, set on the temp file's descriptor, so the umask does not narrow or widen it, and 0755 with `Runnable`; under `KeepMode` the old file's mode, 0644 where there is none | given with `Mode`, in either order, refused matching `fs.ErrInvalid` before anything is made, on every system; `Swap` refuses it, and `Append` refuses it converted to a `LogOption`. Windows: the temp file is made with no access list of its own, so it holds its folder's inheritable entries alone and is not read-only: who reads the file is the folder's say, which can be wider or narrower than 0644; a volume with no access lists takes it. Over an old plain file under `KeepMode` or `KeepOwner` the file has the owner-only list, as without `Shared`; over a file the folder's list reaches, as the first such write made, `KeepMode` is refused matching `ErrNoMode` when that list grants another account, as for any old file that does. `Keep` and `PutBack` take it and do not apply it |
| `KeepMode()` | the mode of the plain file replaced; `Mode`'s, or 0600, when there is none or a link is there | Windows: the read-only attribute of the file replaced is kept, and the new file has the owner-only list. A file whose list grants any account but this one, SYSTEM and Administrators, or has a NULL list, and a name that is neither a plain file nor a link, as a junction or a reparse point of a driver's own tag, are `ErrNoMode`, before anything is made; `Keep` refuses it with `ErrNoMode` |
| `Owner(uid, gid)` | the owner, on the temp file's descriptor before it is in place; -1 leaves either | Windows: `Owner(-1, -1)` is taken and changes nothing; any other ids, a negative one included, are `ErrNoOwner`, which matches `errors.ErrUnsupported` |
| `KeepOwner()` | the owner and group of the plain file replaced, on the temp file's descriptor before it is in place, read by a look at the name that follows no link; `Owner`'s, or the writer's, when there is none or a link is there. An account that may make names in the folder can choose them, as it can the mode `KeepMode` keeps | Unix: one this account may not give (another account, or a group it is not in, without root) is refused, matching `fs.ErrPermission`, and nothing is replaced. Windows: a file this account owns is kept exactly; one another account owns, Administrators among them, as for an elevated program's plain write, and a name that is neither a plain file nor a link, as a junction or a reparse point of a driver's own tag, are `ErrNoOwner` before anything is made; `Keep` refuses it with `ErrNoOwner` |
| `NoReplace()` | puts the file in place by a hard link from the temp file, then removes the temp name, so of two writers one wins | a taken name, a link included: an error matching `fs.ErrExist`; a volume with no hard links: `ErrNoHardLinks`; a temp name that cannot be removed once the file is linked: an error that says the file is in place and its temp file is left, given after the rest of the write has run, the folder's flush included |
| `NoSync()` | flushes neither the file nor its folder, for a file made again every few minutes; still replaced whole. On Windows the rename is not written through | |
| `Check(fn)` | runs `fn` on the temp file, read from its start through the read-only descriptor the write holds till its last check, opened while the written one was still open, before the file is put in place. Under `Runnable` it runs outside the fork lock, so it may run the file it checks | `fn`'s error: the old file stays and no temp file is left. A file swapped in at the temp name is refused, and is never the file `fn` reads |
| `Runnable()` | for a file that is run soon after: on Linux, macOS and BSD the temp file's create, write, flush and close hold `syscall.ForkLock`'s read side, which a fork takes the write side of, so no child of this process is forked holding the write descriptor. Linux and FreeBSD refuse to run a file open for writing (`ETXTBSY`, text file busy) until every such child execs or exits. The lock holds only this process's own forks, not another program's. A reader given to `FileFrom` is read whole into memory before the lock is taken, so it may start a process or make a pipe or a socket, which would otherwise wait on the lock for ever. Bound a large or untrusted reader with `io.LimitReader`, since all of it is held at once. The file is 0700 unless `Mode` or `KeepMode` gives another. To ask whether this system would run a file in a root, call `confine.IsRunnable`: on Unix it reads the exec bit that applies to this account, on Windows the extension against `PATHEXT`, and follows no link. `exec.LookPath` on an absolute path follows links, and on Windows asks only for a dot in the name, not `PATHEXT` | |
| `IfHolds(sum)` | writes only if the file at the name is a plain file whose SHA-256 is `sum` | another SHA-256, or no file: `ErrChanged`; a link, a folder or a pipe at the name: an error that is not `ErrChanged` |
| `LogMode(perm)`, `Append`'s alone | the mode of a log `Append` makes, at first and after each move, exactly, set on the descriptor of the exclusive create, so the umask does not narrow it; a log already there keeps its own | a mode that does not give the owner read and write, as `Append` opens the log for both; Windows: `ErrNoMode`. Each before the log is opened or made, so no line is written |
| `Aside(name)`, `Append`'s alone | the name beneath the root a full log is moved to, over a plain file there; `Append` has no default and refuses with `ErrNoAside` without it | the log's own name: as written or cleaned (`./c.log`, `sub/../c.log`) before anything is opened, and in a spelling only the volume reads as the log (another case where the volume ignores it, a trailing dot or space on Windows) when the log is to be moved, by the file at it being the log; a link or anything not plain at it when the log is to be moved |

A folder that cannot be flushed after the rename gives `ErrNotDurable`: the new file is in place, and the write is not to be done again. On Windows it is a volume that refuses to write the rename through, which then renames plainly. Which volumes refuse it is not known: NTFS on a fixed disk, exFAT on a removable one and, measured on one FAT32 volume, FAT32 all take the write-through open and the flush, so none gives `ErrNotDurable`, though a write on FAT32 is refused first, for want of access lists (`ErrNoAccessList`, below). An SMB share is not yet probed. A volume that takes the flag and does not honour it answers as one that does, and nothing here can tell them apart: the rename is then as durable as the volume makes it.

A write, a `Swap` and an `Append` each check that the file they put in place, hold or move is the one they looked at, by the volume serial and the 64-bit file index `os.SameFile` reads (the device and inode number on Unix). A file whose index reads zero or all-ones cannot be told apart from another, so each reads the index of a handle it holds and refuses with `ErrNoFileIndex`, which matches `errors.ErrUnsupported`, rather than trust the compare. A zero index is a volume's answer: every file on a volume that keeps no file IDs (a WebDAV drive, some SMB servers) reads zero, and `os.SameFile` does not test the index for zero, so one read settles it. An all-ones index is one file's answer: ReFS, whose real file ID is 128-bit and does not fit the 64 bits read, returns all-ones for some files, so the index is read file by file, not volume by volume. Reading ReFS's 128-bit ID to tell its files apart is not planned. `heldBy`, the compare a kept-mode or kept-owner write makes, refuses a no-index file as the rest do, and `NoReplace`'s second look at a name it just linked leaves a no-index file there rather than take it away. `ErrNoFileIndex` is one value, which `confine`, `lock`, `appdirs`, `treesum` and `trust` refuse their own compares by file ID with too, so `errors.Is(err, write.ErrNoFileIndex)` holds of each. FAT32 answers a non-zero index from the directory entry (measured on one FAT32 volume), so it is not a no-index volume, though such an index is weaker than an NTFS one, as it can recur for a new file made in a freed entry; exFAT was not measured. A write on FAT or exFAT is refused earlier, for want of access lists. `Append` to a name where no log is there yet makes the empty log before it has a handle to read the index of, so on a no-index volume it may leave that empty log and then refuse; no line is written.

`SyncFolder(root, dir)` flushes a folder beneath a root, for a change in it that no write here made: a removal, a file made by an exclusive create, a folder made. It is `root.OpenFile(dir, os.O_RDONLY|O_NONBLOCK, 0)` and `Sync`, with a `Stat` to refuse what is not a folder, since `Sync` on a file flushes the file and says nothing. A `dir` that is missing, not a folder, or reached through a link out of the root is an error on every system, and the open never waits, so a pipe at `dir` is refused at once. On Windows, which flushes a folder only through a handle open to write, the folder is opened again by its own handle, to write, with backup semantics, and `FlushFileBuffers` flushes it. A volume that will not flush it is an error matching `errors.ErrUnsupported`, and a folder this account may not write to, or another process holds sharing no write, is that open's error; none is answered as flushed.

## What holds on each system

| | Linux, macOS, BSD | Windows |
|---|---|---|
| replaced whole, by a rename over the name | yes | yes; a read-only old file is made writable for the rename, and read-only again if the rename fails |
| a reader that opened the old file | reads the old bytes to the end | reads the old bytes to the end when it opened the file through an `os.Root`, as this package does, which shares the file for delete; on exFAT the write is refused instead, as access denied once the tries below are spent, while any reader holds the old file, which stays as it was |
| a temp file, an old file, or a log at its cap, held for a moment by another process | | the rename is tried again for about 600 ms: a sharing violation when the file moved is held, an access denial when the file replaced is (a reader through `os.Open`); an access list's denial looks the same, so it too reaches the caller about 600 ms late. The window is a fact of the system, how Windows answers a scanner or an indexer that holds a file for a moment, not a value of the caller's, so no option lengthens or shortens it; a caller that must answer sooner has its own context on `Append`'s wait |
| the folder flushed after the rename | yes | no: Windows refuses the flush of a folder opened to read, access denied, on NTFS and exFAT alike. A write's rename is written through to the disk instead, as `MoveFileEx` does with `MOVEFILE_WRITE_THROUGH`, but by the folder's handle beneath the root, not by a path that a folder swapped for a link could lead out of: the temp file is opened with `FILE_WRITE_THROUGH` and renamed relative to its folder. A volume that refuses the write-through open gets the plain rename and `ErrNotDurable`; NTFS and exFAT take it. Under `NoSync` the rename is plain. `NoReplace`'s link and `Keep`'s copy are kept by the file system's log alone, and report nothing |
| the file made | 0600, or `Mode`'s, set on its descriptor | an access list only this account and SYSTEM reach, none of its folder's inherited, set by the create itself, so the file is never there with another; a replace keeps no list (`KeepMode` over a file other accounts reach is refused), so a file other accounts read is given its list by the program after the write. A volume that keeps no access lists (FAT, exFAT), and a folder where this account cannot open by name what it makes with that list (a restricted token or an AppContainer the list does not name, a share that knows this account by another SID), are refused with `ErrNoAccessList`, which matches `errors.ErrUnsupported`, and `fs.ErrPermission` too where the cause is a denial, so test `ErrNoAccessList` first, and nothing is made, so every write is refused there, a replace included; `Append` to a log there writes as before until its first move, whose new log is refused. Whether this account can open by name what it makes with that list is tried first on a throwaway file beside it, `.probe-` and random letters, made and removed, and only where the name is not there already: under a restricted token or in an AppContainer the list does not name, which must also pass its restricting SIDs or its package, it cannot, and nothing is made. A process killed in that instant leaves the throwaway file, empty, and it is the caller's to remove, and so does a removal of it that fails, with an error that names it and is `ErrNoAccessList` only where it could not be opened by name either |
| `Mode` | applied | the access list above, narrower than the mode, and the read-only attribute where the mode has no owner write; one without owner read, or with setuid, setgid or sticky, refused with `ErrNoMode` |
| `Shared` | 0644, or 0755 with `Runnable`, on the descriptor | no access list of its own: the folder's inheritable entries alone, not read-only, and taken on a volume with no access lists; the owner-only list over an old plain file under `KeepMode` or `KeepOwner`, and in `Keep` and `PutBack`. The temp file is reachable under the folder's list while it is written |
| `LogMode` | applied to the log `Append` makes, on its descriptor | refused with `ErrNoMode` before the log is opened or made, so no line is written |
| `Owner` | applied | `Owner(-1, -1)` taken, and the file is the writer's; any other ids, a negative one included, refused with `ErrNoOwner` |
| `Runnable` | the create to the close under `syscall.ForkLock`'s read side; 0700 unless a mode is given | nothing held: a child inherits only the handles made inheritable, and a write's are not; the file has the access list above |
| `KeepMode` | applied | the read-only attribute kept, with the access list above; over a file whose list grants any account but the writer's, SYSTEM and Administrators, refused with `ErrNoMode`, and so is a name that is neither a plain file nor a link, as a junction or a reparse point of a driver's own tag, a cloud-files placeholder among them where one shows its tag (a config in a synced folder, for one) |
| `KeepOwner` | applied | over a file the writer's account owns, taken; over another account's, refused with `ErrNoOwner`, and so is a name that is neither a plain file nor a link, as a junction or a reparse point of a driver's own tag, a cloud-files placeholder among them where one shows its tag |
| `Keep`, `PutBack` | the copy's source's mode, on the descriptor, its group bits cleared unless the copy, owned, is in the source's group or `Owner`'s: a file 0640 copied into a folder whose group the copy takes is 0600 there. Nothing is chowned to match; `Owner` alone gives a group | the read-only attribute of the source, the file in `Keep` and kept in `PutBack`, with the access list above, whether or not a `Mode` is given |
| `SyncFolder` | the folder opened beneath the root and flushed | the folder opened beneath the root, opened again by its handle to write, and flushed by `FlushFileBuffers`; a volume that will not is `errors.ErrUnsupported` |
| `NoReplace` | by a hard link | by a hard link; on a volume that keeps access lists and no hard links (some SMB servers), refused with `ErrNoHardLinks`, and on FAT and exFAT, which keep neither, refused first with `ErrNoAccessList`. A mode without owner write leaves the placed name read-only, read once it is in place and set again where the remove of the temp name took it off; one that cannot be set is the write's error |
| `Append`'s hold on the log, waited on until the caller's context ends | `flock(2)` | `LockFileEx` on one byte past any log's end |
| a log's count of names, for a hard link | `st_nlink`; once held, from the `Lstat` that matched the log | `NumberOfLinks`, through the handle; once held, after the `Lstat` that matched the log and an open of the log by its name that shares no delete until the line is written or the log moved: a name removed before that open is tried again, and its remove after it, a rename over it, a rename over it of another name of the held file and then its remove, or a hard link made over it with replace, gets no line. A short name does not reach that name: a hard link put at the log's name has none, and a short name reaches it only where the held file's first name was moved there, which takes the power to move the target, no new reach |
| a volume that reports one name for a file of two | the count is as good as the volume's `st_nlink`: on a mount that reports 1 (some FUSE and SMB mounts), a hard link to a file outside the root gets the line | the count is as good as the volume's `NumberOfLinks`, the same way |
| a pipe at a name read or appended to | refused at once | there are no named pipes in a folder |
| a name that is not clean, or has a component ending in a dot or a space | taken as `os.Root` takes it: a name that leads out is refused | refused before a write opens anything, with an error matching `fs.ErrInvalid`: `os.Root`'s calls go by the Win32 name rules, which strip a trailing dot or space, and the written-through rename does not, so `app.toml.` would be hashed and read as `app.toml` and written beside it. A name that is not local, a device name such as `NUL` among them, is `os.Root`'s own refusal, in its words, as on every system. `Append` to a log whose last name ends in a dot or a space is refused too, before anything is opened, matching `fs.ErrInvalid`: nothing is made, and a log at the stripped name is left as it was |

- **What it does not hold**: an account that can write the folder can remove and remake the temp name between the last check and the rename on Unix, where the rename goes by the name. `NoReplace` on Windows links by the handle opened at the temp name and compared with the file written, so a file put there since the last check is never linked, and none is taken away: where the swap took the written file's last name, NTFS refuses the link, and the write is refused as swapped with nothing at the name. A swap that leaves the file written a name, the temp name renamed aside, does not refuse the write: the file written is linked and keeps the name it was renamed to, and the other file is removed from the temp name or, where its account holds it open without delete sharing, left there, and the write says so. On Unix no call links a descriptor on every system, so `NoReplace` links by the temp name, and a file put there since the last check is at the name from the link until the write has read the name against the file written, which it holds open from the last check, so no other file can take its inode: a process that opens the name in that moment has the other file. The write then takes it away and is refused as swapped. The take-away is of that file's own name, made only while the name still shows it, so a name another process made at that moment is left, but a file another process renames over the name in the moment between the link and the first look is taken away as the swapped one, on either system; where it fails, the error says the swapped file is in place. A mode without owner write leaves the placed name read-only, as above. Every rename on Windows, written through or not (`NoSync`, or a volume that refuses write-through), goes by the handle opened at the temp name and compared with the file written while the write still holds that file, and kept open to the rename, so no other file can take its record, and a file put there since the last check is never renamed. From the close up to the last check, a file put there is refused on every system. A close that fails on the handle held to the end of the write, once the file is in place, is an error that says so.
- **What it imports**: the standard library, `confine` and `internal/fileid`, and on Windows `golang.org/x/sys/windows` and the module's Windows calls. The layer rows of the root's [.golangci.yml](../.golangci.yml) say so, and `task lint` holds them on every system.

`go doc github.com/birdtable/go-files/write` has the rest; every exported name is documented.

## Libraries looked at

The standard library and `golang.org/x` first.

| looked at | why it falls short, or what it gives | verdict |
|---|---|---|
